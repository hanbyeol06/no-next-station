# 《다음 역은 없습니다》 데이터 기반 콘텐츠 확장 기획

**문서 버전:** 0.1  
**기준 문서:** [게임 역기획서](게임-역기획서.md)  
**목표:** 공통 게임 코드를 고치지 않고 데이터 팩만 추가해 사건, 근무, 역 구역과 결말을 늘릴 수 있는 구조를 정의한다.

> 보관본입니다. 현재 승인된 데이터 구조와 제작 절차는 [정본 GDD 목차](../../README.md), 특히 콘텐츠 구조와 제작 로드맵을 따릅니다.

## 1. 기획 목표

현재 프로토타입은 다섯 호출의 대사, 정답 번호, 기록, 장면 반응이 게임 코드 안에 함께 들어 있다. 호출을 추가하거나 내용을 바꾸려면 게임 로직도 함께 수정해야 한다.

목표 구조에서는 다음을 분리한다.

| 계층 | 책임 | 콘텐츠를 추가할 때 변경 여부 |
|---|---|---|
| 게임 런타임 | 호출 진행, 화면 전환, 점수 계산, 입력 처리, 저장 및 공통 효과 | 지원 중인 규칙 안에서는 변경하지 않음 |
| 콘텐츠 데이터 | 에피소드, 호출, 대사, 증거, 선택지, 판정, 결과 문구 | 새 콘텐츠마다 추가 |
| 장면·표현 데이터 | 카메라 구역, 화면 구성 요소, 상태별 시각·음향 효과 | 기존 장면 부품을 조합하면 추가 |
| 플레이 세션 상태 | 현재 호출, 열어 본 자료, 선택 이력, 신뢰도, 잔향 | 실행 중 런타임이 관리. 콘텐츠 원본은 수정하지 않음 |
| 번역 데이터 | 버튼·UI·사건 텍스트의 언어별 문구 | 새 언어 또는 번역 추가 시 추가 |

**완료 기준:** 기존 상호작용 규칙으로 만들 수 있는 새 근무와 호출은 콘텐츠 팩 파일만 추가해 플레이할 수 있다. 새로운 조작이나 새로운 종류의 판정이 필요할 때만 런타임을 확장한다.

## 2. 콘텐츠 계층 구조

콘텐츠는 다음과 같이 묶는다.

**세계/노선 → 에피소드 → 근무 → 호출 → 증거·선택지·결과**

- **세계/노선:** 역의 공통 배경, 역 구역, 카메라와 시간표 형식
- **에피소드:** 하나의 이야기를 구성하는 근무 묶음
- **근무:** 플레이 가능한 짧은 회차. 호출의 순서와 근무 판정표를 가진다.
- **호출:** 플레이어가 판단하는 한 사건. 발신 내용, 확인 자료, 선택, 결과를 연결한다.
- **증거:** CCTV, 운행표, 이전 통화, 근무 일지 등 플레이어가 열람하는 자료
- **선택과 결과:** 방송/침묵 문구, 판정 조건, 기록 변화, 화면 반응

새 사건은 기존 역 구역과 상호작용을 재사용할 수 있다. 새 역이나 새 화면이 필요하면 장면 데이터도 함께 추가한다.

## 3. 런타임과 데이터의 책임 경계

### 런타임 코드가 담당할 일

- 콘텐츠 팩을 읽고 ID 참조가 유효한지 확인한다.
- 호출 순서에 따라 전화, 자료 화면, 선택지, 결과 화면을 표시한다.
- 공통 판정 규칙을 평가하고 세션 상태를 갱신한다.
- 선언된 장면 효과를 적용한다. 예: 셔터 상태 변경, 실루엣 표시, 안내등 점등, 효과음 재생.
- 현재 근무의 점수와 잔향을 결말 프로필과 비교한다.
- 자료 종류와 장면 템플릿을 공통 UI로 렌더링한다.

### 콘텐츠 데이터가 담당할 일

- 어떤 호출이 어느 순서로 나오는지
- 호출자의 문장, 발신 위치, 현장 메모
- 어떤 자료가 어떤 탭에 보이는지
- 어떤 문장을 선택할 수 있는지
- 이 사건에서 어떤 선택이 기록 기준에 맞는지
- 선택 결과로 어떤 문구·장면 효과·점수 변화가 발생하는지
- 어떤 누적 상태에서 어떤 결말이 선택되는지

### 데이터만으로 만들 수 있는 범위

새 호출, 새로운 대사, 새로운 증거 조합, 기존 효과의 재사용, 호출 순서 변경, 근무별 점수 임계값과 결말 문구는 데이터만으로 추가할 수 있게 한다.

새로운 핵심 입력(예: 마이크 자유 발화), 새로운 게임 규칙(예: 카메라 확인 중 전력 소모), 기존에 없는 증거 형식이나 완전히 새로운 장면 렌더링은 먼저 런타임 기능으로 추가해야 한다. 데이터 파일 안에 임의의 코드를 실행시키지는 않는다.

## 4. 데이터 계층 상세

### 4.1 팩 목록과 버전

팩 목록은 사용할 콘텐츠의 ID, 파일 경로, 버전, 기본 언어를 정의한다. 콘텐츠 팩은 서로 독립적으로 켜고 끌 수 있어야 한다.

팩 필수 정보:

- 고유한 packId와 schemaVersion
- 표시 이름, 설명, 기본 언어
- 에피소드 ID 목록
- 호환되는 런타임 최소 버전

### 4.2 노선·역·장면

장소 데이터는 역 ID, 구역 ID, CCTV 피드, 표시 이름과 재사용 가능한 장면 템플릿을 가진다. 호출은 “2번 출구”를 직접 그리는 대신 zoneId 또는 feedId를 참조한다.

장면은 기존 프로토타입처럼 모든 그림을 코드에 하드코딩하지 않고, 공통 요소의 조합으로 표현한다.

- 템플릿 예: 출구, 승강장, 복도
- 요소 예: 문, 셔터, 표지판, 바닥선, 조명, 원경, 인물 실루엣
- 각 요소의 위치·크기·표현 ID
- 초기 상태와 사건 반응별 상태 변화

새 요소를 자유로운 SVG 문자열이나 코드로 삽입하는 방식은 피한다. 승인된 장면 요소와 상태 조합만 데이터로 선언한다.

### 4.3 에피소드와 근무

근무 데이터는 에피소드 ID, 근무 제목, 시작/종료 시각 표시, 호출 ID와 순서, 점수/잔향 프로필, 결말 프로필 ID를 가진다.

호출 순서를 바꾸거나 호출을 추가해도 진행 엔진은 그대로 동작한다. 특정 호출 ID를 코드에서 직접 비교하지 않는다.

### 4.4 호출과 증거

호출은 아래 정보를 참조형으로 가진다.

- 사건 ID, 제목, 화면에 표시할 시각
- 발신자 이름/장치, 통화 문구, 보조 음성 설명
- 기본 카메라 피드
- 플레이어가 확인할 자료 ID 목록
- 사용 가능한 선택지 목록
- 판정 규칙과 결과 참조

증거는 공통 타입을 사용한다.

| 증거 타입 | 필드 예시 |
|---|---|
| CCTV | feedId, 시각, 관찰 문구, 사건 전/후 장면 상태 |
| 운행·시설 기록 | 시각, 구역 ID, 기록 내용, 상태 |
| 통화 기록 | 발신 ID, 통화 내용, 반복/이상 표시 |
| 근무 일지 | 기록 작성자, 기록 내용, 기록 신뢰 상태 |
| 센서 | 구역 ID, 센서 종류, 관측 값, 정상 범위 |

새 사건에서 기존 증거 타입을 재사용하면 UI 코드를 추가할 필요가 없다. 새 증거 모양이 기존 타입과 다르면 먼저 그 타입의 공통 표시 방식을 구현한다.

### 4.5 선택·판정·결과

선택지는 표시할 문구와 효과를 데이터로 가진다. 판정 로직은 제한된 선언형 조건만 지원한다.

지원할 기본 판정:

- 특정 선택지 ID와 일치
- 여러 조건을 모두 만족(AND)
- 여러 조건 중 하나를 만족(OR)
- 세션 수치가 지정 임계값 이상/이하
- 이전 사건에서 특정 상태 플래그가 설정됨

지원할 공통 효과:

- 기록 신뢰도 또는 잔향 증감
- 호출 로그에 문구/사건 결과 추가
- 장면 상태나 장면 효과 ID 적용
- 후속 호출의 대사/증거 변형 플래그 설정
- UI 결과 문구와 선택 피드백음 재생

효과 이름과 인자는 고정된 스키마로 검증한다. 조건식이나 효과에 실행 코드를 넣지 않는다.

### 4.6 결말 프로필

근무 종료 데이터는 결말 후보와 조건을 가진다. 조건은 점수 임계값, 잔향, 플래그의 조합으로 선언한다.

- 결말 ID, 제목, 설명, 화면 표현 ID
- 조건 우선순위
- 필수/금지 상태 플래그
- 기록 신뢰도 및 잔향 범위

각 가능한 세션 상태에서 적용할 결말이 하나만 선택되도록 우선순위와 범위를 검사한다. 근무별로 결과 문구와 결말 수를 바꿔도 엔진은 바뀌지 않는다.

### 4.7 번역과 UI 문구

UI 고정 문구와 사건 콘텐츠 문구를 분리한다. 각 언어 파일은 키와 번역 문자열을 담고, 콘텐츠는 직접 문장을 중복 삽입하는 대신 문구 키를 참조할 수 있다.

- UI 번역: CCTV, 방송, 다음 호출, 근무 판정 등 공통 버튼
- 콘텐츠 번역: 호출 대사, 증거 문장, 선택지, 피드백, 결말
- 번역이 누락된 키는 선택한 기본 언어로 대체하고 개발 모드에서는 누락 경고를 표시한다.

      stations/
        station-04.js
      scenes/

기존의 index.html은 공통 런타임과 팩 목록 로더를 한 번 연결한다. 이후 새 근무는 game-data/packs에 팩을 추가하고 manifest의 데이터 목록에 ID를 등록한다. 런타임 파일은 수정하지 않는다.

### 로컬 파일 실행 방식

현재 프로토타입은 브라우저에서 HTML 파일을 직접 열 수 있도록 외부 라이브러리와 서버를 사용하지 않는다. 이 실행 방식을 유지하려면 정적 JSON을 fetch로 읽는 구조에 바로 의존하지 않는다. 권장 초기안은 고정 런타임 로더가 일반 스크립트 파일을 읽고, 각 팩은 JSON과 같은 순수 데이터 객체만 등록하는 방식이다. 로컬 실행과 정적 호스팅 양쪽을 유지할 수 있다.

팩 파일에는 함수나 실행 로직을 넣지 않는다. 콘텐츠는 프로젝트 내부에서 관리하고, 외부 사용자가 임의 팩을 가져오는 모드가 생길 경우에는 데이터 검증과 허용 효과 목록을 별도로 적용한다.

## 6. 호출 데이터 예시

아래 예시는 현재 1번 호출을 새 스키마로 옮기는 형태다. 실제 구현 전에 ID 규칙과 스키마 버전을 확정한다.

    {
      "id": "exit-02-closed",
      "timeLabel": "00:17",
      "titleKey": "incident.exit02.title",
      "caller": {
        "type": "station_phone",
        "displayKey": "incident.exit02.caller",
        "messageKey": "incident.exit02.call"
      },
      "primaryFeedId": "station04.exit02",
      "evidenceIds": [
        "evidence.exit02.cctv",
        "evidence.exit02.maintenance"
      ],
      "choices": [
        {
          "id": "announce_closed",
          "textKey": "choice.exit02.closed",
          "judgement": "verified",
          "effects": [
            { "type": "scene_state", "target": "station04.exit02.shutter", "value": "locked" },
            { "type": "add_record_trust", "value": 1 }
          ],
          "feedbackKey": "result.exit02.closed"
        },
        {
          "id": "announce_open",
          "textKey": "choice.exit02.open",
          "judgement": "unverified",
          "effects": [
            { "type": "scene_state", "target": "station04.exit02.shutter", "value": "open" },
            { "type": "add_echo", "value": 1 }
          ],
          "feedbackKey": "result.exit02.open"
        },
        {
          "id": "remain_silent",
          "textKey": "choice.silence",
          "judgement": "unverified",
          "effects": [
            { "type": "add_echo", "value": 1 }
          ],
          "feedbackKey": "result.exit02.silence"
        }
      ]
    }

판정에 따라 달라지는 점수와 장면 상태는 효과 데이터로 표현한다. 런타임은 scene_state, add_echo, add_record_trust처럼 이미 구현된 효과를 해석한다. 새 효과 타입 자체가 필요하면 런타임 작업이 필요하다.

## 7. 현재 프로토타입에서의 이전 대상

| 현재 코드 내 요소 | 이동할 데이터 계층 |
|---|---|
| 다섯 호출의 시간·제목·통화 문구 | 호출 데이터 |
| 시간표 행·현장 메모 | 증거 데이터 |
| 정답 선택지 번호 | 판정 데이터의 선택지 ID |
| 선택 후 문구·점수 변화 | 선택 효과 데이터 |
| SVG 안의 역 공간 배치와 사건별 변화 | 장면 템플릿/장면 상태 데이터 |
| 엔딩 점수 경계와 문구 | 결말 프로필/번역 데이터 |
| 탭·점수계·호출 진행 UI | 공통 런타임과 화면 템플릿 |
| 실행 중 현재 사건·점수·잔향·선택 로그 | 플레이 세션 상태 |

### 필수 런타임 리팩터링

현재 game.js는 사건 데이터, 판정, SVG 장면을 모두 직접 보유한다. 따라서 “데이터 파일만 추가”하는 제작 방식은 아직 적용되어 있지 않다. 먼저 다음을 한 번 구현해야 한다.

1. 다섯 호출의 데이터와 텍스트를 런타임 코드 밖으로 이동한다.
2. 배열 위치/호출 순서에 의존하는 분기를 사건 ID와 데이터 참조로 바꾼다.
3. 점수 판정과 결말 선택을 범용 평가기로 이동한다.
4. 장면의 배치와 변화를 공통 장면 요소/상태로 표현한다.
5. 팩 로더와 데이터 검증기를 추가한다.
6. 기존 다섯 호출을 새 구조로 재구성해 현재 흐름과 결과가 유지되는지 확인한다.

리팩터링이 끝나면 지원 중인 자료 타입, 장면 요소, 판정 조건, 효과의 조합으로 콘텐츠를 확장한다.

## 8. 콘텐츠 추가 작업 절차

1. 새 콘텐츠 팩 ID와 에피소드 ID를 정한다.
2. 기존 역·카메라·증거 타입을 재사용할지 확인한다.
3. 근무 순서와 호출 목록을 작성한다.
4. 호출마다 최소 한 개 이상의 확인 자료를 연결한다.
5. 방송 문구와 침묵 선택지를 작성한다.
6. 판정, 현장 피드백, 기록/잔향 효과를 데이터로 선언한다.
7. 결말 프로필과 번역 문구를 추가한다.
8. 데이터 검사기로 ID 중복, 참조 누락, 미지원 효과, 번역 누락, 결말 조건 충돌을 확인한다.
9. 로컬 브라우저에서 새 팩을 선택해 해당 근무를 플레이한다.

콘텐츠 기획자는 이 절차에서 데이터 편집을 담당하고, 프로그래머는 새 상호작용 규칙·증거 타입·장면 부품을 추가할 때 런타임을 확장한다.

## 9. 콘텐츠 설계 가이드

새 호출은 기존 플레이 감각을 유지할 수 있도록 다음 항목을 갖춘다.

- 호출자의 구체적인 요구와 발신 출처
- 서로 대조할 수 있는 자료 두 개 이상
- 플레이어가 관찰 가능한 정상/이상 단서
- 명확히 판정할 수 있는 선택지와 침묵/보류 선택
- 선택 직후 확인할 수 있는 현장 반응 또는 기록 변화
- 다음 사건의 이해를 돕거나 불안을 누적하는 한 문장

콘텐츠 데이터는 표현만 바꾼 세 가지 오답을 반복하지 않는다. 사건마다 “무엇을 알고 싶은가”, “어떤 말을 망설이는가”, “침묵은 어떤 위험을 갖는가”가 달라야 한다. 정답이 불명확한 서사를 원할 경우, 채점 기준과 이야기 속 확실성은 별도 필드로 두어야 한다.

## 10. 성공 조건과 경계

### 데이터 기반 확장의 성공 조건

- 신규 근무/호출 추가를 위해 game engine이나 화면 코드를 편집하지 않는다.
- 팩 ID·사건 ID·증거 ID의 참조 오류가 실행 전 검사된다.
- 콘텐츠와 플레이어의 임시 세션 값이 섞이지 않는다.
- 점수/잔향·결말 기준이 코드 상수 대신 프로필 데이터로 관리된다.
- 기존 화면 요소로 표현할 수 없는 콘텐츠가 무엇인지 명확하게 드러난다.

### 데이터만으로 늘릴 수 없는 변화

데이터 계층은 콘텐츠를 많이 만드는 수단이지, 모든 새 게임 규칙을 코드 없이 만드는 시스템은 아니다. 자유 음성 인식, 카메라 감시 자원, 이동/은신, 실시간 추적 적처럼 플레이어의 행동 모델을 바꾸는 기능은 엔진 개발이 선행되어야 한다.

현재 프로토타입의 핵심 루프와 다섯 사건의 역기획은 [게임 역기획서](게임-역기획서.md)를 참고한다.
